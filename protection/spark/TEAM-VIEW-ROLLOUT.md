# Включение «Обзора команды»

Статус: включено 28 ноября 2026 года после отдельного подтверждения владельца. В рабочей базе сохранены все 82 сделки; проекция сверена с актуальными личными записями. На опубликованном сайте проверены суммы, расшифровки и фильтры. Чтение общей сводки с ограниченными правами менеджера разрешено, чтение чужого личного профиля и анонимное чтение отклоняются. Тариф Spark сохранён. Не считать этот документ подтверждением других изменений и не применять правила автоматически из CI.

## Объём прав

Подтверждённые аккаунты из закрытого `/spark/access` получают чтение актуальных финансовых строк всех менеджеров: клиент, техника, даты, компания, сумма, маржа, тип/статус, бонус, возврат и доля инвестора. Также доступны месячные планы. Это позволяет раскрыть все показатели общей сводки. Чужие исходные записи, контакты, закупочные цены, комментарии, история и корзина остаются закрытыми. Права редактирования исходных профилей не расширяются.

Изменения правил ограничены тремя местами:

- Новый `/spark/teamView`: чтение активным подтверждённым аккаунтам; изменение строки только вместе с допустимой актуальной записью своего профиля (руководителю — любого); планы меняет руководитель. Флаг `enabled` клиентам недоступен для записи.
- Валидация новой версии `sales`: при включённой проекции проверяется её точное соответствие новой версии; корзина удаляет финансовую строку.
- Такая же проверка для `plans`.

Остальные правила должны побайтово совпасть после нормализации JSON с сохранённой рабочей версией. В частности, не менять `/data`, `/presence`, `/dashboard`, список доступа и реестр машин. Это проверено на рабочем снимке правил при подготовке.

## Последовательность после подтверждения

1. Убедиться, что нет чужих новых изменений `main`, проверить тесты. Сохранить свежие частные копии правил и `/spark` вне Git. Сверить предложенные правила с текущими: кроме указанных трёх мест отличий быть не должно; иначе остановиться для разбора.
2. Применить подготовленные `database.rules.json` к существующему проекту `bm-avto`, пока `teamView/enabled` отсутствует. Новая связанная проверка пока отключена, старые вкладки сохраняют записи как прежде.
3. Опубликовать согласованную версию из корня репозитория в `main`, дождаться успешного GitHub Pages. Проверить HTML и версии `auth.js`, `store.mjs`, `model.mjs`. Адрес остаётся прежним.
4. Через Admin SDK в **транзакции на `/spark`** построить `buildTeamView(current.profiles)` из данных, прочитанных самой транзакцией, и добавить как `current.teamView`. Сохранить все остальные свойства текущего состояния без изменений. Если проекция уже включена — остановиться для проверки, а не затирать её. При первом пустом локальном состоянии вернуть `null` для повторного чтения серверного значения. Не загружать снимок, сделанный ранее, поверх текущей базы.
5. Сверить проекцию с `buildTeamView` свежего текущего состояния и проверить отсутствие изменений личных записей от самой активации. Проверить ноябрьскую сводку, несколько расшифровок, другой месяц, выбор менеджера, личный кабинет и сохранение. Не создавать вымышленные продажи в рабочей базе.
6. Попросить сотрудников обновить открытые вкладки. Старая версия после активации не сможет сохранить изменение финансовых полей без атомарного обновления проекции; форма при отказе сохраняется. Новая версия подписана на флаг и обновляет проекцию при сохранении.

Если включение не прошло, сначала сохранить свежую базу и разобраться. Не восстанавливать старые личные записи поверх новых. При необходимости Admin SDK может отключить флаг (не удаляя личные записи), а затем убрать только добавленную проекцию/новые правила после проверки. Простой откат HTML при включённом флаге приведёт к отказам сохранения; он не является достаточным откатом.
